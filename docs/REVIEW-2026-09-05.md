# 개인용 Plaud Note Manager 실행·성능·기능 검토

- 검토일: 2026-09-05
- 대상: 현재 개인용 `~/DEV/plaud-note-manager` 체크아웃과 기존 `/Applications/Plaud Note Manager.app`
- 근거: `README.md`, `docs/APP-FEATURES-AND-DESIGN.md`, `docs/SPEC.md`, `docs/PLAN-v0.6.md`, `docs/PLAN-v0.7.md`, `docs/PLAN-v0.8.md`, `docs/REQUESTS.md`, `STATUS.md`, Swift/Python 진입점
- 성격: §1–4는 수정 전 결함과 기능 범위의 감사 기록, §5는 구조 개선 제안이다. 이번 0.8.1에서 반영한 내용과 실행 검증은 §6에 구분한다. 완료 표시가 없는 확장 제안은 구현된 기능이 아니다.

앱은 녹음 관리, 전사, 모델별 요약, Dual 통합, 분류, Obsidian 송출까지 이미 연결되어 있다. 이번 개선의 우선순위는 실행과 반응성을 회복하고, 작업 성공·실패와 결과 파일을 정확히 표시하는 것이다. 기존 계획서의 미완료 표시는 상당수가 오래되었으므로 기능을 새로 추가하기 전에 현재 코드와 구분해야 한다.

## 1. 검토 기준과 현재 버전

검토 시작 시 직접 읽은 설치본은 `0.8.0`, build `32`, source `e0695b9-dirty`다. 소스 `pyproject.toml`은 `0.8.0`, Git HEAD는 `ad1344d`, 최신 tag는 `v0.5.1`이다. 따라서 버전 숫자만 같다고 설치본에 현재 변경이 들어 있다고 볼 수 없다. 설치본은 뒤의 변경을 포함하지 않은 개인용 빌드다.

CLI를 Python에서 등록 목록으로 읽어 확인한 명령 수는 **101개**다. 이 조회는 외부 계정이나 생성 모델을 호출하지 않았다. `STATUS.md`의 약 70개 및 `SPEC.md`의 약 75개 표기는 과거 기록이다.

상태는 다음 기준을 사용한다.

| 상태 | 판정 기준 |
|---|---|
| 구현 | UI 또는 CLI 진입점에서 실제 core/저장 경로까지 연결 |
| 조건부 구현 | 코드가 연결되어 있으나 Plaud 로그인, vendor CLI, ElevenLabs, 볼트 경로 등이 필요 |
| 부분 구현 | 일부 표면, 실패 복구, 설정 또는 저장 계약이 미완성 |
| 계획 | 소스에 연결된 실행 경로가 없음 |
| 라이브 미검증 | 이번 감사에서 원격 읽기·변경, 유료 생성, 볼트 송출을 실행하지 않음 |

## 2. 실행과 속도를 해치는 수정 전 결함

설치본 실행을 재현한 담당자의 process sample(`/tmp/plaud-before.sample.txt`)에서는 CPU 약 99.3%와 메인 스레드의 `TagNode`/`ForEach` outline diff가 관찰됐다. 같은 DB를 읽기 전용으로 확인한 집계는 전체 녹음 1,574개, 비휴지통 녹음 1,489개, 태그 6,301개이며 이 태그는 모두 평면 이름이었다. 이 설치본에서는 수천 개 태그를 한 번에 구성하는 사이드바가 실제 시작 정지의 주요 관측 지점이다. 다른 대기·경로 결함도 별도로 수정해야 하며 CPU sample 하나로 모든 느린 동작을 설명하지 않는다.

| 우선순위 | 확인한 원인 | 사용자에게 나타날 수 있는 현상 | 필요한 수정 |
|---|---|---|---|
| P0 | 6,301개 평면 태그를 재귀 노드/outline로 한 번에 구성하며 SwiftUI main-thread diff 발생 | 실행 직후 창이 응답하지 않고 CPU가 높게 유지 | 태그 검색과 제한된 초기 목록, 더 보기, 안정된 ID. 긴 태그 목록 전체를 초기 렌더하지 않음 |
| P0 | `FileStore.runPlaud`와 `runPlaudOutput`이 stdout/stderr를 읽기 전에 `waitUntilExit()` 호출 | CLI가 pipe 용량 이상 출력하면 자식은 출력 완료를 기다리고 앱은 자식 종료를 기다림. Sync/Deep Sync/생성이 끝나지 않을 수 있음 | 두 pipe를 동시에 소비하는 공용 실행기, 반환되는 종료 상태, timeout과 종료 처리 |
| P0 | `Database.fetchModelPresetsFromCLI`가 별도 subprocess 구현, stderr 미소비, timeout 없음 | 설정·모델 목록 조회가 외부 실행 환경에 붙잡힘 | 공용 실행기 재사용, 캐시, 제한 시간, UI와 분리된 조회 |
| P0 | `PlaudCommand.makeProcess`가 매번 `uv run plaud` 실행 | 이미 준비된 개인용 `.venv`가 있어도 uv의 환경 확인·캐시·경로 문제에 영향받음 | 정상 `.venv/bin/plaud` 직접 실행 우선, 필요한 경우에만 uv fallback |
| P0 | `sync(showError: false)`가 명령 성공을 반환받지 않고 `lastSyncedAt` 갱신. 인증 복구는 표시용 `lastCommandError` 문자열에 의존 | 백그라운드 sync가 실패해도 동기화 시각이 갱신되고, 숨긴 오류에서는 인증 복구 분기가 빠짐 | 성공 여부를 데이터로 전달하고 성공한 sync만 시각 갱신. 오류 표시 여부와 복구 판단 분리 |
| P1 | 여러 `@Published` 속성, 전체 라이브러리 reload, 선택 상세 reload가 넓은 View 트리에 전파됨 | 작은 상태 변경도 긴 전사·슬롯 출력의 재평가와 디스크 접근을 유발 | 목록·선택 상세·작업 상태별 snapshot, 중복 reload 합치기, View body의 DB/파일 조회 제거 |
| P1 | 폴더 이동·제목 변경이 로컬 DB를 먼저 쓰지만 원격 실패 복구가 없음 | 화면에는 성공처럼 보이나 다음 sync에서 원복되거나 Cloud와 다른 상태 유지 | 변경 전 값 보관, 원격 실패 시 해당 변경만 복구 또는 pending 표시 |
| P1 | Python의 integrated path override와 Swift Final/Work Sidebar 기본 경로가 다름 | 생성은 성공했는데 Final이 비거나 Finder가 다른 폴더를 엶 | 하나의 output path 계약으로 쓰기·읽기·진행률·Finder 경로 통일 |
| P1 | Swift 설정 기본 Grok backend는 `api`, Python 기본은 `cli` | 설정 파일에 값이 없을 때 Settings 표시와 실제 호출 방식이 어긋남 | 동일한 기본값과 설정 계약 사용 |
| P1 | `classify-undo`의 인자와 metadata 복구가 불완전 | Undo가 실패하거나 일부 상태만 되돌림 | 원래 폴더와 metadata를 명시적으로 복구하고 실패 항목의 매니페스트 보존 |
| P1 | metadata upsert의 INSERT 기본값이 conflict UPDATE에도 재사용되어 “None이면 기존 상태 보존” 계약 위반 | 분류·metadata 수정이 기존 read/usage 상태를 unread/unused로 되돌릴 수 있음 | INSERT 기본값과 UPDATE 의도를 분리하고 수명주기·기존 metadata 보존 회귀 검증 |
| P1 | `sync-content`가 항목별 실패를 출력한 뒤 `done N/N`으로 정상 종료 | 개수 표시가 성공 수로 오해되며 전체 실패도 정상 종료로 보일 수 있음 | 처리/성공/실패/남은 수 구분, 실패 상태 반환 |
| P1 | 패키징이 기존 설치 위치를 지운 뒤 복사 | 복사 실패 시 사용 가능한 기존 앱도 없어짐 | 완성 번들 검증 후 staging 교체, 복구 가능한 이전 설치 보존 |

이 표는 소스에서 확인한 실패 조건이다. 각 원인이 이번 사용자의 모든 증상을 일으켰다는 단정이나 수치화된 속도 개선 주장은 별도의 실행 측정 없이는 하지 않는다.

## 5. 구조 개선 제안과 순서

아래는 감사 당시의 제안이다. 공용 subprocess 실행기, 태그 행·Markdown·slot snapshot,
reload 합치기 등 이번에 채택한 범위는 §6에 기록한다. FileStore 전체 분리, artifact index,
범용 작업 큐와 독립 daemon 등은 후속 제안으로 남는다.

### 5.1 먼저 실행 경계와 상태 계약을 정리

**PROPOSE:** Swift의 모든 CLI 호출을 하나의 `PlaudProcessRunner`로 통합한다. UI는 stdout 문자열과 alert 유무로 성공을 추측하지 않고 종료 코드, stdout, stderr, timeout 상태를 받는다. stdout/stderr를 실행 중 소비하고, 조회 명령과 장기 생성 명령에 각각 적절한 제한 시간을 둔다. 최소 회귀 조건은 대용량 양쪽 출력, 비정상 종료, timeout, stdin 전달이다.

**PROPOSE:** `uv` 의존성을 매 클릭에 노출하지 않도록 준비된 `.venv/bin/plaud`를 우선 사용한다. 앱 시작 시 설치된 binary, runtime, DB 위치와 오류를 구분한다. `/Applications` 설치본을 교체한 후 버전·SHA·실제 실행 경로를 검증해야 한다.

### 5.2 표시용 읽기와 작업 실행을 분리

**PROPOSE:** `FileStore`를 Library, Selection, Jobs, Auth 상태로 나누되 한번에 모든 UI를 재작성하지 않는다. 우선 자주 변하는 작업 spinner/오디오 상태가 라이브러리와 긴 전사 렌더를 모두 다시 계산하지 않게 경계를 만든다. DB 결과와 artifact 본문은 View body 밖에서 읽고, 선택 ID·파일 signature·generation으로 캐시를 갱신한다.

현재 파일 규모는 `ContentView.swift` 약 6,000행, `FileStore.swift` 약 1,700행, `Database.swift` 약 1,650행, `cli/main.py` 약 3,200행이다. 행 수 자체가 성능 원인은 아니지만 실행, 저장, 표현의 책임이 한곳에 섞여 있어 회귀를 찾고 격리하기 어렵다. 기능별 파일 분할은 이 경계를 명확히 만드는 순서로 진행한다.

### 5.3 DB와 artifact 계약을 한곳에 정의

**PROPOSE:** Python은 schema migration과 Cloud/생성 작업을 소유하고 Swift는 짧은 로컬 UI 쓰기와 조회를 담당하도록 계약을 명문화한다. 양쪽에 복제된 기본값, 경로, schema를 계약 테스트로 비교한다. migration은 시작 시 한 번 수행하고 일반 read 경로에 schema 변경을 섞지 않는다. 소규모 로컬 쓰기 때문에 library의 긴 content를 재조회하지 않는다.

**PROPOSE:** artifact 경로는 생성, Final, slot, 진행률, locator, Finder reveal이 동일하게 해석한다. 그다음 file ID, kind, model, template, path, mtime, source hash를 가진 작은 artifact index를 검토한다. 기존 Markdown은 보존하고 index는 재생성 가능해야 한다.

### 5.4 작업 큐와 실패 복구를 공용화

**PROPOSE:** Deep Sync, 자동 metadata, ElevenLabs, summarize/integrate, Dual을 한 작업 모델로 표시한다. 작업 ID, recording ID, 단계, 실행 시각, 성공/실패, 취소 가능 여부를 공통으로 둔다. 같은 녹음·같은 생성 종류의 중복 실행을 차단하고, UI 선택이 바뀌어도 이전 작업의 결과가 새 선택을 덮지 않게 한다.

**PROPOSE:** Cloud 변경은 실패한 변경만 복구할 수 있는 원래 값과 요청 결과를 보존한다. 분류는 사용자가 본 preview와 apply 입력을 연결하고 Undo가 실패한 항목은 재시도할 수 있어야 한다. 장기적으로 작업 지속 저장이 필요할 때 기존 Dual 상태 머신을 일반화한다.

독립 Python daemon/XPC 서비스 도입은 아직 필수 조건이 아니다. 먼저 subprocess 정지, 과도한 reload, 경로 중복을 해결하고 측정한다. 그래도 CLI 시작 비용이 주요 병목으로 남을 때만 개인용 worker를 검토하면 운영 복잡도를 제한할 수 있다.

### 5.5 그다음 미완료 기능을 연결

사용 가치가 높은 순서는 Reuse 필터/노트, slot mode 저장, Vault root Settings, custom folder icon 재편집, 장기 작업 취소다. 새로운 STT backend·iOS·범용 chat·완전 자동 scheduler는 현재 실행 복구와 기존 기능 완결 뒤로 둔다. Cloud pagination은 이번 §6 범위에 반영했으며, 삭제/move reconciliation은 별도 설계가 필요하다.

## 6. 검증 계약

이 문서 담당자는 문서·소스·등록 CLI 목록·설치 plist를 읽었고, 실행 sample·DB 집계·설치본 UI는 같은 세션의 실행 복구 담당자가 직접 확인한 결과를 전달받았다. 팀은 만료된 Plaud session 복구를 시도했으나 성공하지 못했다. ElevenLabs/LLM 실행, Cloud 변경, Obsidian 송출은 이번 개선의 라이브 성공으로 주장하지 않는다. 과거 문서의 E2E 성공과 단위 테스트 수를 이번 빌드의 검증으로 사용하지 않는다.

패키징 코드는 같은 세션에서 개선했다. 고유 staging 디렉터리에서 bundle을 완성하고 plist/signature를 검증한 뒤 교체하며, 기존 dist와 설치 앱은 각 staging 디렉터리의 `Previous Plaud Note Manager.app`으로 보존한다. 마지막 rename 실패 시 이전 앱을 복구한다. 강제 재귀 삭제를 제거했고 `PlaudBuildTimestamp`, `PlaudSourceFingerprint`로 미커밋 개인 빌드도 구별한다. 패키징 담당자는 `bash -n`과 diff 공백 검사를 완료했고, 실행 복구 담당자는 최종 release build·설치·실행을 §6.2와 같이 검증했다.

### 6.1 0.8.1 소스에 반영한 범위

- 6,301개 태그를 초기 80행·더 보기·전체 검색으로 표시하고, 안정적인 평면 행 ID와 background 계산을 사용한다.
- `PlaudProcess.swift`가 기존 `.venv/bin/python -m cli.main`을 직접 실행하고 stdout/stderr를 실행 중 소비한다. 조회 30초, sync/detail 120초, 일반 장기 작업 2시간 제한을 적용한다.
- 명령 성공·실패를 반환하여 실패한 sync의 마지막 성공 시각을 갱신하지 않고, 숨긴 오류에서도 인증 복구 판단을 수행한다.
- library reload는 동시에 하나만 실행하며 중복 요청을 합친다. 같은 값의 publish를 줄이고 Markdown·slot 결과·CMDS 상세를 background snapshot으로 읽는다.
- 선택이 바뀐 뒤 이전 audio URL이 새 녹음에 적용되는 것을 막고, custom integrated 경로를 Final·slot·Finder reveal에 연결한다.
- cached/total은 모두 비휴지통 기준으로 계산하고 자동 backfill은 새 DB 집계로 판단한다. 기본 Grok backend 표시를 Python과 동일한 CLI로 맞춘다.
- Cloud sync는 active/trash pagination과 페이지 단위 batch 저장을 수행한다. 반복 페이지를 오류로 판단하고, `sync-content`는 부분 실패를 비정상 종료로 보고한다.
- metadata upsert의 lifecycle 보존과 분류 metadata merge를 수정한다. 새 분류 Undo는 변경 전후 snapshot, 수동 변경 conflict 검사, 실패 manifest 보존 및 여러 override 그룹 연결을 제공한다. 구형 manifest는 원래 snapshot이 없어 제한된 호환 복구만 가능하다.

일반 폴더 이동·제목 변경의 원격 실패 rollback, 범용 작업 큐/취소 UI, Cloud 삭제 reconciliation, Reuse 확장 UI 등은 이번에 구현한 것으로 보지 않는다.

### 6.3 완료 판단과 성능 측정 조건

이번 수정의 완료 판단에는 다음 구분이 필요하다.

1. 코드: Python/Ruff, 변경 범위의 Swift 테스트와 release build 통과.
2. 회귀: large stdout/stderr, timeout, DB query/경로 override, 잘못된 성공 표시, metadata 보존 등 수정한 실패 조건 검증.
3. 설치: `/Applications`에 실제 새 bundle 배치, source provenance 확인.
4. 앱: 설치본 창 생성, 라이브러리 표시, 선택 변경, 검색, 긴 transcript, Settings에서 응답성 확인.
5. 외부 서비스: 현재 계정의 sync·auth와 유료 생성·Cloud 변경·Vault 송출을 각각 별도로 기록.

성능 수치는 같은 DB·같은 recording·같은 build 설정에서 비교해야 한다. 시작→창, 시작→첫 목록, 녹음 선택→첫 상세, 긴 전사 스크롤, 검색→결과를 각각 측정하고 초기 cache 상태·반복 횟수를 함께 남긴다. 측정 전에는 “몇 배 빨라졌다” 또는 전체 라이브 환경을 검증했다는 표현을 쓰지 않는다.

self_docked: Dual metadata가 Cloud 폴더를 이동한다는 초기 의심은 core와 CLI wrapper를 구분해 확인한 뒤 기각했다. 소스상 결함만으로 실제 실행 불능의 단일 원인을 확정하지 않았다. 인증 복구와 sync는 시도했으나 성공하지 못했다. 유료 AI/STT 생성, Cloud 변경, Vault 송출은 실행하지 않았다. 단일 CPU snapshot을 성능 향상 배수로 해석하지 않았으며, 계획서의 과거 성공·비용·모델 가용성을 현재 실측으로 재사용하지 않았다.
